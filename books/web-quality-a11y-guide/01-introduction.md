## Web品質の定義

「Web品質」とは、Webサイトやアプリケーションがユーザーに提供する体験の総合的な水準を指す。具体的には以下の4つの軸で構成される。

1. **アクセシビリティ（a11y）** -- 視覚・聴覚・身体・認知に障害を持つユーザーを含む、すべての人がコンテンツを利用できること
2. **パフォーマンス** -- ページの読み込み速度、インタラクションの応答性、リソース効率
3. **セマンティックの正確さ** -- HTMLの構造が意味的に正しく、機械（ブラウザ、スクリーンリーダー、検索エンジン）が内容を正確に解釈できること
4. **倫理的な設計** -- ユーザーを欺いたり操作させたりするダークパターンを排除し、透明で誠実なインターフェースを提供すること

これら4つは独立した概念ではなく、相互に作用する。セマンティクスの欠如はアクセシビリティを損ない、パフォーマンスの低下は認知障害を持つユーザーへの影響が特に大きい。ダークパターンはアクセシビリティ違反と表裏一体になっている場合も多い。

Web品質は「追加の機能」ではない。建築物の耐震性や防火性と同じく、設計段階から組み込むべき基盤的な要件である。

### 品質は後からでは取り返せない

Web品質に関する問題は、プロジェクトの後期になるほど修正コストが増大する。セマンティクスを無視してdivとspanだけで構築されたUIは、後からアクセシビリティ対応しようとすると大幅なリファクタリングが必要になる。フォームのバリデーションが視覚的な赤枠だけで実装されている場合、aria-invalidやaria-describedbyを後付けするにはマークアップ構造自体の変更が避けられない。

これは技術的負債の一種であり、初期設計でセマンティックHTMLと基本的なARIA属性を組み込んでおくだけで回避できるコストである。

## アクセシビリティがWeb品質の土台である理由

WCAG（Web Content Accessibility Guidelines）はW3Cが策定する国際標準であり、2024年4月に改正された障害者差別解消法により、日本でも民間事業者に合理的配慮の提供が義務化された。法的義務の有無に関わらず、アクセシビリティ対応はユーザー全体の利便性を向上させる。

- キーボード操作への対応はパワーユーザーの生産性を高める
- セマンティックHTMLはSEOに直接貢献する
- 適切なコントラスト比は屋外でのモバイル利用時にも有効に機能する
- 構造化されたマークアップは保守性と可読性を向上させる

アクセシビリティを「特別な対応」として後付けするアプローチはコストが高く、品質も低くなる。本書ではアクセシビリティを設計の起点として扱う。

### 数字で見るアクセシビリティの現状

WebAIMが毎年実施している調査 ([WebAIM Million](https://webaim.org/projects/million/)) によると、2026年版では上位100万サイトのホームページの95.9%で、自動検出できるWCAG 2の不適合が見つかっている。前年の94.8%から悪化した。検出数の多い6項目は次のとおりで、この顔ぶれは7年間変わっていない。

1. **低コントラストのテキスト** -- 83.9%のサイトで検出
2. **画像のalt属性の欠如** -- 53.1%
3. **フォーム入力のlabel欠如** -- 51.0%
4. **空のリンク** -- 46.3%
5. **空のボタン** -- 30.6%
6. **言語属性の欠如** -- 13.5%

数値は2026年版の時点のものである。毎年更新されるため、引用するときは版を確かめる。

これらはいずれもセマンティックHTMLの基礎的な知識で防止できる問題である。高度なARIAの知識以前に、基本的なHTMLの書き方を見直すだけで大幅な改善が見込める。

## 本書の対象読者

本書は以下の読者を想定している。

**デザイナー**

- コンポーネント設計時にアクセシビリティ要件を組み込みたい方
- Dialog、Table、FormなどのUIパターンの適切な使い分けを学びたい方
- ダークパターンの判断基準を体系的に理解したい方

**フロントエンドエンジニア**

- セマンティックHTMLとARIAの実装知識を体系的に整理したい方
- Dialogやフォームのアクセシビリティ対応を正しく実装したい方
- スクリーンリーダーでの動作確認方法を学びたい方

**デザイナーとエンジニアの両方**

- Web品質の全体像を把握し、チーム内で共通認識を持ちたい方
- WCAGの達成基準を実務に落とし込んだ具体例を求めている方

本書はデザインとエンジニアリングの両方の視点を横断的に扱う。特定のフレームワークに依存しない知識を中心に据えつつ、実装例はHTML/CSSおよびReact（JSX）で記述する。

## 前提知識

本書を読み進めるにあたり、以下の知識を前提とする。

**必須**

- HTMLの基本的な要素と属性（div, span, a, button, input, form等）
- CSSの基本（セレクタ、ボックスモデル、Flexbox）
- Webブラウザの開発者ツール（Elementsパネル、Console）の基本操作

**あると望ましい**

- Reactの基本（コンポーネント、Props、State、useEffect）
- TypeScriptの基本的な型記法
- npm / pnpmなどのパッケージマネージャの操作経験

Reactの知識がなくても各章の概念的な説明とHTML/CSSのコード例は理解できる。React固有の実装パターン（useRefによるdialog制御、カスタムHook等）については、該当箇所で補足を加えている。

## WCAGの基本構造

本書で頻繁に参照するWCAG（Web Content Accessibility Guidelines）の基本構造を簡潔に整理しておく。

WCAGは以下の4つの原則で構成されている。

| 原則 | 英語 | 概要 |
|---|---|---|
| 知覚可能 | Perceivable | すべてのユーザーがコンテンツを知覚できること。代替テキスト、字幕、十分なコントラスト等 |
| 操作可能 | Operable | すべてのユーザーがUIを操作できること。キーボード操作、十分な時間、発作を起こさない設計等 |
| 理解可能 | Understandable | コンテンツと操作方法が理解できること。読みやすいテキスト、予測可能な動作、入力支援等 |
| 堅牢 | Robust | 支援技術を含む様々な環境で正しく動作すること。標準準拠のマークアップ等 |

適合レベルはA（最低限）、AA（標準）、AAA（最高）の3段階がある。一般的なWebサイトではAA準拠が目標とされる。本書の内容は主にAおよびAAレベルの達成基準に対応している。

## 本書で扱わない内容

- バックエンドのアクセシビリティ（PDF生成、メール配信等）
- ネイティブアプリ（iOS / Android）のアクセシビリティ
- WCAG達成基準の網羅的な解説（本書は実務で頻出するパターンに焦点を当てる）
- パフォーマンス最適化の詳細（Core Web Vitals、バンドルサイズ削減等）

## 本書の表記規則

コード例にはすべて言語とタイトルを付記している。「悪い例」と「良い例」を対比する構成を多用しているが、これは「悪い例」のコードが常に間違いであるという意味ではない。コンテキストによっては許容される場合もある。重要なのは、なぜその書き方が問題になりうるかを理解することである。

本書では以下の表記規則を用いる。

- `:::message` -- 補足情報、関連する知識
- `:::message alert` -- 注意が必要な事項、よくある間違い
- `:::details` -- クイズやコーディングチャレンジ（開閉式）
- コード例中の `{/* コメント */}` -- JSX内のコメント。React固有の記法

:::message
各章の末尾にはクイズとコーディングチャレンジを設けている。理解度の確認に活用してほしい。
:::

## 開発環境の準備

本書のコード例を手元で試すために、最低限以下の環境を準備しておくとよい。

- モダンブラウザ（Chrome, Firefox, Safariのいずれか）
- ブラウザの開発者ツール（F12で起動）
- スクリーンリーダー（macOSならVoiceOver、WindowsならNVDA）

スクリーンリーダーの詳細な操作方法は「セマンティックHTMLとARIA」の章で解説する。初めて使う場合でも、基本的な起動・終了とTabキーでのナビゲーションができれば十分である。

Reactのコード例を動かしたい場合は、Node.js（v18以上）と任意のパッケージマネージャ（npm, pnpm, yarn）があれば `npx create-react-app` や `npx create-next-app` で素早く環境を構築できる。

Web品質は一度達成すれば終わりというものではなく、継続的な改善の対象である。本書がその第一歩となれば幸いである。
