## TL;DR

Google Labs が 2026-04-21 に公開した **DESIGN.md** を、実際に導入して測りました。

- **出自**: Google Stitch から切り出されたもの。リポジトリの homepage が Stitch のドキュメントを指しています
- **実測1**: 実在する DESIGN.md **74件**を機械測定したところ、**2つの流派**があり、**公式サンプルは実物の分布の外**にありました（重なりゼロ）
- **実測2**: 仕様どおりに書くと**黙って値が消える**箇所が7件。全て npm 公開物で再現しました
- **実測3**: 「実装が仕様を守っているか」を LLM に判定させたら、**判定可能な12項目すべて正解・誤検出ゼロ**。そして**判定できない項目には「分からない」と答えました**

最後の実験がこの記事の主題です。**「できていないこと」が見えている系は安全で、「できているように見える」系が一番危険**、という話をします。

検証に使った資料とコードは公開しています。

- 解説: https://github.com/BoxPistols/design-md-docs
- 実験環境と再現手順: https://github.com/BoxPistols/design-md-docs/blob/main/docs/07-machine-verification.md

:::message
検証時点: フォーマット `alpha` / CLI `@google/design.md@0.4.0` / 2026年8月。
フォーマットは draft 段階のため、記述が実装に追いつかなくなる可能性があります。
:::

## 1. DESIGN.md とは何か

コーディングエージェントに、**ビジュアルアイデンティティを持たせるための1ファイル**です。

```md
---
name: Heritage
colors:
  primary: "#1A1C1E"
  tertiary: "#B8422E"
---

## Overview

高級マット紙の質感 — 上質なブロードシート紙か、現代的なギャラリーの図録。

## Colors

- **Primary (#1A1C1E):** 見出しと本文のための深いインク。
- **Tertiary (#B8422E):** インタラクションを駆動する唯一の色。
```

YAML front matter が機械可読なトークン、Markdown 本文が人間可読な根拠。エージェントはこの1ファイルを読むだけで、セッションをまたいでも同じ視覚言語で UI を生成できる、という設計です。

### 出自 — Google Stitch から出てきた

ここは推測が流通しやすいので、一次証拠を示します。

**GitHub リポジトリの homepage が Stitch のドキュメントを指しています。** リポジトリ所有者自身が設定したメタデータです。

```console
$ gh repo view google-labs-code/design.md --json homepageUrl
{"homepageUrl":"https://stitch.withgoogle.com/docs/design-md/specification"}
```

そして [Google 公式ブログ](https://blog.google/innovation-and-ai/models-and-research/google-labs/stitch-design-md/)（2026-04-21）のタイトルがそのまま答えです。

> **Stitch's DESIGN.md format is now open-source so you can use it across platforms.**

[Stitch](https://stitch.withgoogle.com/) は Google Labs の AI UI 生成ツールです。そこで使われていた内部フォーマットを、他のツールでも使えるように切り出した、という経緯になります。

| | |
|:--|:--|
| リポジトリ作成 | 2026-04-10 |
| 公式アナウンス | 2026-04-21 |
| ライセンス | Apache 2.0 |
| 状態 | `version: alpha`（Google 自身が "draft specification" と表記） |

**この出自は後で効いてきます。** 「公式サンプルがなぜあの形なのか」の説明になるからです。

### Google は何と言っているか（正確に）

ここは公平に引用します。**Google の主張は precise で、控えめです。**

> DESIGN.md in Stitch lets you **export or import your design rules from project to project**, so you don't have to reinvent the wheel every time you start a design in Stitch.

> AI agents can know exactly **what a color is for**, and can **validate their choices against WCAG accessibility rules**.

注目してほしいのは2つ目です。Google が検証能力として名指ししているのは **WCAG だけ**です。「デザインとして正しいことを検証できる」とは**一言も言っていません**。

後で見るように、これは**正確な記述**です。ツールは WCAG コントラストを本当に検証します。問題は Google の主張ではなく、**読み手が勝手に広げてしまう推論の方**にあります。

## 2. 導入と設置

### インストールと4つのコマンド

```bash
npx @google/design.md lint DESIGN.md
```

```json
{
  "findings": [
    {
      "severity": "warning",
      "path": "components.button-primary",
      "message": "textColor (#ffffff) on backgroundColor (#1A1C1E) has contrast ratio 15.42:1 — passes WCAG AA."
    }
  ],
  "summary": { "errors": 0, "warnings": 1, "infos": 1 }
}
```

| コマンド | 用途 | 終了コード |
|:--|:--|:--|
| `lint` | 構造検証。JSON で findings を返す | error があれば `1` / 読めなければ `2` |
| `diff` | 2つの DESIGN.md を比較し回帰を検出 | 回帰があれば `1` |
| `export` | Tailwind v3/v4・CSS変数・DTCG へ変換 | 成功 `0` |
| `spec` | 仕様書そのものを出力（プロンプト注入用） | — |

`spec` が地味に効きます。エージェントに仕様そのものを食わせられるので、「DESIGN.md の書き方を知らないモデル」にも書かせられます。

### ライブラリとしても使える

```typescript
import { lint } from '@google/design.md/linter';

const report = lint(markdownString);
report.findings;      // Finding[]
report.summary;       // { errors, warnings, infos }
```

### 最初に踏む罠

**Windows**: `.md` 拡張子がファイル関連付けと衝突します。`designmd` エイリアスを使ってください。

```bash
npx -p @google/design.md designmd lint DESIGN.md
```

**stdin が効かない**: README には「すべてのコマンドはファイルパスまたは `-`（stdin）を受け付ける」と書いてありますが、**`lint` / `diff` / `export` の3つとも動きません**。

```console
$ cat DESIGN.md | npx @google/design.md@0.4.0 lint -
 ERROR  Missing required positional argument: FILE
```

ヘルプ自身が `FILE  Path to DESIGN.md (use "-" for stdin)` と表示するのに、その `-` で落ちます。原因は引数パーサ（citty が内部で使う mri）が**単独の `-` を positional から落とす**ことです。

回避策があります。**`--` を挟むと通ります。**

```bash
cat DESIGN.md | npx @google/design.md@0.4.0 lint -- -
```

## 3. 実測1 — 実物74件を測る

仕様書だけ読んでも「で、みんなどう書いてるの？」は分かりません。測りました。

対象は [VoltAgent/awesome-design-md](https://github.com/VoltAgent/awesome-design-md) という有志のコレクションで、airbnb / apple / figma / nike / notion / nvidia / spotify / tesla など実在ブランドの DESIGN.md が74件入っています（**公式ではなくコミュニティ製**です）。

測定スクリプトは公開しているので、誰でも再現できます。

```bash
git clone --depth 1 https://github.com/VoltAgent/awesome-design-md.git /tmp/awesome
python3 tools/measure.py /tmp/awesome/design-md
```

### 発見1: 2つの流派がある

きれいに二極化していました。

| | **スキーマ型** | **散文型** |
|:--|:--|:--|
| 件数 | 64 / 74 | **10 / 74** |
| トークン | あり（中央値268行） | **1行も無い** |
| セクション | `Overview` `Colors`…（仕様の名前） | `1. Visual Theme & Atmosphere` 〜 `9. Agent Prompt Guide` |
| 例 | airbnb, apple, figma, notion | spotify, tesla, starbucks, mastercard |

散文型の10件は、**色の値を1つも書いていません。全部が文章です**（starbucks は450行）。しかも10件が10件とも同じ9セクション構成です。

**どちらも `lint` を通ります。** 値が決まっていない段階では散文型で始められる、というのは実務的に重要な選択肢です。

### 発見2: 公式サンプルは実物の分布の外にある

同じ物差しで、本家リポジトリ同梱の `examples/` 3件も測りました。

```
実物64件（スキーマ型）  トークン比率  中央値 57.7%   範囲 48.1% 〜 68.2%
公式サンプル3件         トークン比率  中央値 80.4%   範囲 77.3% 〜 80.7%
                                                      ↑
                      実物の最大 68.2% ＜ 公式の最小 77.3%  ← 重なりゼロ
```

散文の量で見ると差はもっと露骨です。

| | トークン行数（中央値） | 散文行数（中央値） |
|:--|--:|--:|
| 実物64件 | 268 | **206** |
| 公式サンプル3件 | 144 | **37** |

**5.6倍**の開きです。

#### なぜこうなっているか — 出自で説明がつく

公式サンプル3件は、色数が**きっちり47個で一致**し、命名も `surface-container-lowest` / `on-primary-fixed-variant` / `inverse-on-surface` と **Material Design 3 の体系そのまま**です（ここまでは実測）。

ここから先は推論ですが、**Stitch 由来という出自を踏まえると自然に読めます**。テーマ生成ツールの出力をそのままサンプルに置いたのだろう、と。

そしてここに、この形式の面白い捩れがあります。本家の `PHILOSOPHY.md` はこう言っています。

> **トークンの値はコンテキストであって、レンダリング指示ではない。**
> 一般に、仕様の中でトークンの要件を定めることは受け入れないし、推奨もしない。

`PHILOSOPHY.md` 冒頭の模範例は、機械可読部分が **`name:` 1行だけ**で、あとは全部プロースです。

- **思想** は「散文が主、トークンは従」
- **実物** は散文とトークンがほぼ拮抗（206 対 268）
- **公式サンプル** はトークンが8割

**3つとも違う方を向いていて、思想から最も遠いものが公式サンプルになっています。**

実務的な結論は1つです。**手本にすべきは公式サンプルではなく、実物の中央値です。**

### 発見3: 仕様に無いセクションが定着している

正準8セクションに含まれないのに、**過半数が使っている**見出しが3つありました。

| セクション | 使用率 | 中身 |
|:--|--:|:--|
| **Responsive Behavior** | 51 / 64（80%） | ブレークポイントと各幅での振る舞い |
| **Iteration Guide** | 50 / 64（78%） | **エージェントに修正を指示する手順** |
| **Known Gaps** | 43 / 64（67%） | **まだ定義していない領域の宣言** |

後ろ2つは仕様がまったく想定していない**運用のためのセクション**です。

**`Known Gaps` は特に効きます。** 書いていないとエージェントは未定義領域を勝手に埋め、しかも毎回違うやり方で埋めます。「ここは決まっていない」と明示するだけで、少なくともそれがチームに共有される。

**これは本記事の主題の先取りでもあります。** 「決まっていないこと」を可視化するセクションが、誰にも指示されずに自然発生して定着した。現場は分かっているわけです。

## 4. 実測2 — 仕様どおりに書くと壊れる箇所

ここからが本題に近づきます。全項目、**npm で公開されている `@google/design.md@0.4.0`**（ソースではなく配布物）で再現しました。

7件見つかりました。**CLI が明示的にエラーにするのは stdin の1件だけ**で、**値が消える・不正な出力が出る類はすべて無警告・終了コード0**です。つまり CI を通しても気づけません。

### 4-1. YAML の素の数値が黙って消える

仕様書は `lineHeight` を「Dimension **または単位なし数値**」と規定し、**仕様書自身のサンプルが `lineHeight: 1.1` を使っています**。

しかし YAML の**数値として**書くと、値は捨てられます。**文字列にすれば通ります。**

```yaml
typography:
  body:
    lineHeight: 1.5      # 数値 → 消える
  body2:
    lineHeight: "1.5"    # 文字列 → 通る
spacing:
  sm: 8                  # 数値 → 消える
  md: 16px               # 文字列 → 通る
```

```console
$ npx -y @google/design.md@0.4.0 export --format css-tailwind P.md
@theme {
  --text-body: 1rem;
  --text-body2: 1rem;
  --leading-body2: 1.5;      ← body の lineHeight は消えた
  --spacing-md: 16px;        ← sm は消えた
}

$ npx -y @google/design.md@0.4.0 lint P.md
  summary: { errors: 0, warnings: 0 }     ← 何も言わない
```

しかも `token-summary` は「1 spacing token」と報告します。**消えた後の数を数えるので、失われたことに気づく手段がありません。**

**回避策**: frontmatter の値は原則すべてクォートする。

### 4-2. `components` 以外の壊れた参照が無警告で消える

`broken-ref` ルールは「解決しないトークン参照は **error**」と説明されていますが、**実際に検査されるのは `components` セクションだけ**です。

```yaml
colors:
  primary: "#1A1C1E"
  accent: "{colors.nope}"    # 存在しないトークンへの参照
```

```console
$ npx -y @google/design.md@0.4.0 lint P.md
  summary: { errors: 0, warnings: 0 }        ← 無警告・exit 0

$ npx -y @google/design.md@0.4.0 export --format css-tailwind P.md
@theme {
  --color-primary: #1a1c1e;                  ← accent が丸ごと消えている
}
```

### 4-3. 不正な CSS を出力する

```yaml
colors:
  bad-hsl: "hsl(120, 100, 50)"        # レガシー記法（S/L に % が無い）
  bad-alpha: "hsl(120 100% 50% / -1)" # アルファが負
```

```console
@theme {
  --color-bad-hsl: #ff00ff;      ← 色相120（緑）のはずがマゼンタ
  --color-bad-alpha: #00ff00-ff; ← CSS として構文エラー
}
```

`#00ff00-ff` はテーマファイルに混入すると、その宣言が丸ごと無効になります。**ビルドは通り、実行時に色が当たらない**という壊れ方です。

**回避策**: 色は `#RRGGBB` で書く。仕様自身も互換性の理由で hex を推奨しています。

### 4-4. 仕様が「エラー」と定める重複見出しが素通り

仕様書は明確に規定しています。

| ケース | 規定 |
|:--|:--|
| 重複するセクション見出し | **エラー。ファイルを拒否** |

実装されていません。同じファイルで順序違反の警告はきちんと出るので、重複だけが見られていません。

**回避策**: 自前で足す。

```bash
grep -E '^## ' DESIGN.md | sort | uniq -d
```

### 4-5. 単位バリデーションがカテゴリ間で不整合

| 書いたもの | lint | export |
|:--|:--|:--|
| `rounded: { bad: 10vh }` | ✅ **error** | ⚠️ **それでも出力する** |
| `spacing: { pct: 50% }` | ❌ 何も言わない | 出力する |

error を検出した値をそのまま出力するのは直感に反します。

---

ここまでで言いたいことは1つです。

> **`lint` が通ったことは、「その DESIGN.md が正しい」ことを意味しません。**

そして次の章で、もっと強い形の同じ問題に行き当たります。

## 5. 実測3 — 実装が仕様を守っているか、機械で判定できるか

### 問題設定

DESIGN.md の検証ツールは**トークンしか見ません**。実測すると、**11個のリントルールのうち Markdown 本文に触れるのは1つだけ**で、それも見出しの並び順しか見ません。`export` も散文を捨てます。

しかも仕様自身は「**散文こそが本体である**」と言っています。

> **この形式は、自分が最重要と主張する部分を検証する手段を持っていません。**

繰り返しますが、これは Google の落ち度ではありません。Google は「WCAG を検証できる」としか言っていない。散文の質を機械判定できると主張した人は誰もいない。**それでも、使う側は「lint が通った」を「大丈夫」と読みます。**

ここを塞げるか、実験しました。

### 実験デザイン

「美術館の展示図録」を参照した DESIGN.md を書き、`Do's and Don'ts` に**視覚的に検証可能な Don't を5つ**置きました。

| | Don't |
|:--|:--|
| **V1** | アクセント色 `#9C3B26` を文字に使わない（ボタンの背景にのみ宿る） |
| **V2** | Bold（font-weight 700 以上）を使わない。最大 600 |
| **V3** | 角丸を 3px より大きくしない |
| **V4** | ドロップシャドウを使わない |
| **V5** | グラデーションを使わない |

同じカード UI を3通り実装します。差分は違反だけです。

| | 違反 |
|:--|:--|
| **A** | **なし**（誤検出テスト用） |
| **B** | V1〜V5 **すべて** |
| **C** | **V2 と V4 のみ**（一番現実的） |

判定器を2つ並走させます。

| | 入力 |
|:--|:--|
| **決定的チェッカ** | computed style（Playwright で走査） |
| **視覚 judge** | **スクリーンショットのみ**（LLM） |

**judge は盲検です。** ファイル名を `sample-1/2/3` に変え、順序も入れ替え、画像内のラベルも消しました。そして重要な指示を1つ入れました。

> 各判定は `violation` / `ok` / **`undetermined`（画像からは判断できない）** のいずれかにしてください。
> **`undetermined` を選ぶことを恐れないでください。分からないものを violation や ok にする方が有害です。**

### 実験の途中で設計が壊れた

スクリーンショットを撮った時点で、**A（font-weight 600）と C（800）のタイトルが視覚的にほぼ同一**であることに気づきました。

Georgia には 600 も 800 も無いため、ブラウザが**両方とも合成ボールドで描く**のです。**CSS 上は明確な違反なのに、ピクセルには差が出ません。**

これは実験の不備ですが、同時に結論を1つ与えます。

> **Don't には「CSS からしか分からないもの」と「ピクセルからしか分からないもの」がある。judge を1種類にすると必ず取りこぼす。**

### 結果1: 決定的チェッカは完璧

```
A（準拠）      : 0 findings          ← 誤検出ゼロ
B（全5違反）   : V1,V2,V3,V4,V5 全検出
C（V2,V4のみ） : V2,V4 だけを正確に
```

**誤検出ゼロ・見逃しゼロ。LLM は1度も呼んでいません。**

### 結果2: 視覚 judge も正解した。そして「分からない」と言った

| | sample-1 = **C**(V2,V4) | sample-2 = **A**(準拠) | sample-3 = **B**(全違反) |
|:--|:--|:--|:--|
| V1 アクセント文字 | ok ✅ | ok ✅ | **violation** ✅ |
| V2 Bold | `undetermined` ⭕ | `undetermined` ⭕ | `undetermined` ⭕ |
| V3 角丸 | ok ✅ | ok ✅ | **violation** ✅ |
| V4 影 | **violation** ✅ | ok ✅ | **violation** ✅ |
| V5 グラデーション | ok ✅ | ok ✅ | **violation** ✅ |

**判定可能な12項目すべて正解。誤検出ゼロ。準拠版を1件も違反にしていません。**

そして **V2 は3枚すべてで `undetermined`**。しかも理由が私の説明より厳密でした。

> ラスタ画像にはフォントウェイトの数値情報が一切載らない。代理指標はステム幅しかなく、実測すると見出しは**ステム/em ≒ 0.18**。「太字域である」ことは言えるが、**600 と 700 の境界はステム幅にして数％で、その位置は書体のウェイト軸に完全に依存する**。書体が同定できない以上、600 か 700 かの割り当ては推測にしかならない。

さらに、私が目視で立てた仮説を**実測で確定**させてきました。

> 見出しのインク画素数が **15661 / 15661 / 15507**。sample-1 と sample-2 は1バイトも違わない。

sample-1 は font-weight 800、sample-2 は 600 です。**ラスタが完全一致している** = ピクセル上に V2 の情報は存在しない、が測定で確定しました。

### 予期していなかった発見

**judge は「見る」のではなく「測る」ことで信頼性を得ていました。** 指示していないのに ImageMagick でピクセル実測を始め、印象ではなく数値で述べています。

> 赤系画素の bbox が **202×76+286+918 = ボタン矩形と完全一致**。見出し・本文・メタの帯はいずれも赤系画素 0。

そして**私が考えていなかった制約**を指摘してきました。

> V3 の「3px」という**絶対 px 閾値の判定は DPR の推定を経由する**。実測は 4 device px で、DPR=2 なら 2px（適合）だが **DPR=1 なら 4px（違反）に反転する**。

正しい指摘です。**絶対単位で書かれた Don't は、原理的に視覚判定に向きません。**

### 設計上の結論

| Don't の種類 | 判定器 | 理由 |
|:--|:--|:--|
| 数値・絶対単位（font-weight, 角丸 px） | **決定的チェッカ一択** | ピクセルに出ない / DPR に依存 |
| 色コード・影・グラデーション | **決定的チェッカ**（judge も取れるが安い方へ） | 両方取れる |
| 余白の印象・階層・参照との一致 | **視覚 judge のみ** | CSS に存在しない |

**視覚 judge は実用になります。ただし「CSS が答えを持っている領域」に使ってはいけません。** そこは決定的チェッカが誤差ゼロ・コストゼロで取ります。judge の価値は、**CSS が表現できないものにしかありません**。

## 6. 一般化 — 「できているように見える」ことが一番危険

ここまでの3つの実測は、全部同じ構造をしています。

| | 表面 | 実際 |
|:--|:--|:--|
| 4-1 数値が消える | `lint` 成功・exit 0 | 値が失われ、件数も減った後の数を報告 |
| 4-2 壊れた参照 | `lint` 成功・exit 0 | トークンごと消滅 |
| 5. 散文の検証 | `lint` 成功 | 散文は**1文字も読まれていない** |

**どれも「動いている」ように見えます。** エラーも出ず、終了コードも 0 で、CI は緑です。

一方、今回の judge が返した `undetermined` は**まったく逆の性質**を持ちます。

- 「V2 は判定できません」と言われた人は、**別の手段を用意します**
- 「V2 は ok です」と言われた人は、**何もしません**

後者の方が体験は滑らかで、成果物は壊れます。

### 「分からない」と言えるかは、設計で決まる

今回 judge が正直に振る舞えたのは、モデルが偉かったからではありません。**そう設計したから**です。

1. **`undetermined` という選択肢を明示的に用意した**
   選択肢に無いものは選ばれません。二値強制は「分からない」を消します
2. **棄権を推奨すると明記した**
   「恐れないでください」「分からないものを断定する方が有害です」と書きました
3. **根拠を必須にした**
   「画像のどこを見てそう言えるか」を要求すると、根拠を書けないものは自然に `undetermined` へ落ちます
4. **盲検にした**
   正解を推測できる情報（ファイル名・順序・画像内ラベル）を全部消しました

**この4つのどれを外しても、結果は変わっていたと思います。** 特に 1 は決定的で、`violation` / `ok` の二値しか渡さなければ、judge は V2 についても**必ずどちらかを答えます**。そしてその答えは、根拠のない推測になります。

### これは DESIGN.md の話ではない

同じ構造は、LLM を評価工程に入れるところ全部にあります。

- コードレビュー agent が「問題ありません」と言う。**読めていない範囲があったかは分からない**
- 要約が滑らかに出てくる。**元文書の欠落部分は、滑らかさの中に溶ける**
- 移行ツールが「完了しました」と言う。**変換できなかったものは、どこにも残らない**

**出力が自信を持って見えることと、その出力が正しいことの間には、何の関係もありません。** そして LLM の出力は、デフォルトで自信を持って見えます。

だから「できないこと」の可視化は、機能ではなく**安全装置**です。

- **`Known Gaps`** — DESIGN.md の実物67%が自然発生的に採用した「未定義領域の宣言」
- **`undetermined`** — 判定器が棄権できる選択肢
- **「lint が通った ≠ 正しい」を明記すること** — ツールの保証範囲を、使う側の期待より狭く言い切る

どれも「機能を減らす」ように見えて、実際には**信頼できる範囲を確定させる**働きをします。範囲が確定していないものは、そもそも使えません。

## 7. 今後のスケーリングをどう見るか

ここは事実ではなく、実測を踏まえた私の見立てです。

### 現状の位置づけ

DESIGN.md は**デザインシステムではありません**。コンポーネントを1つも提供せず、実行時に何も強制しません。デザインシステムの「憲法」部分だけを切り出したものです。

| | 答えること | 作るのに必要なもの |
|:--|:--|:--|
| デザインシステム | どんな部品があり、どう使うか | デザイン組織 |
| **DESIGN.md** | **何に見えるべきか、なぜか** | **良い記述** |

### 伸びるとしたらどこか

**(a) 検証の層が増える方向**

今は「トークンの整合性」しか検証していません。今回の実験が示したのは、**その上に2層足せる**ということです。

```
層3  視覚 judge      … 余白・階層・参照との一致（LLM）
層2  決定的チェッカ   … 実装 vs Don't（computed style）  ← 誰も作っていない
層1  lint            … トークンの整合性（既存）
```

**層2 が空いています。** 今回の実験では誤検出ゼロで動きました。DESIGN.md の `Do's and Don'ts` を機械可読な述語として書けるようにすれば、標準化の余地があります。

**(b) Storybook 等との突き合わせ**

DESIGN.md の `components:` と、実際の story を突き合わせて「定義があるのに story が無い / story があるのに定義が無い」を検出する。既存の `orphaned-tokens` ルールを**境界をまたいで**拡張したものです。

### 伸びにくいと見ているところ

**コンポーネント仕様としては薄すぎます。** サブトークンは8種類しかなく、仕様自身が「components は活発に進化中」と断っています。バリアントは命名規約で表現し、合成も記述できません。ここを厚くする方向は、既存のデザインシステムと正面衝突するので筋が悪いと思います。

**Figma との双方向同期も、当面は来ないと見ています。** `export` は一方向で、戻す経路の設計が始まった形跡がありません。

### 最大の不確実性

**Stitch から切り出された経緯**が、そのまま将来の不確実性でもあります。仕様の進化が Stitch のプロダクト都合に引っ張られるのか、コミュニティの実務に引っ張られるのか。

今のところ後者の兆候があります。仕様に無い `Iteration Guide` / `Known Gaps` が実物の過半数に定着しているのは、**現場が仕様を先回りしている**証拠です。この流れが仕様に取り込まれるかどうかが、当面の見どころだと思っています。

## 8. 導入するなら

実務の推奨だけまとめます。

1. **コンポーネントライブラリは捨てない。** DESIGN.md はその上の意図の層です
2. **値が決まっていないなら散文型で始める。** 実測で10/74件が実在する正当な型です
3. **Overview の参照を1つ、具体的に決める。** 「モダンでクリーン」は領域を指すだけで何も制約しません。「駅の発車標」は点を指します
4. **`Known Gaps` を必ず書く。** 未定義領域は最大の事故源です
5. **frontmatter の値は全部クォートする**（4-1 の回避）
6. **`{参照}` は `components` の中だけで使う**（4-2 の回避）
7. **CI では `lint` に加えて、重複見出しと不正な色出力を自前でチェックする**

7 のサンプルは公開してあります。

## まとめ

- DESIGN.md は Google Stitch 由来で、2026-04-21 に Apache 2.0 で公開された draft 仕様
- **Google の主張は正確で控えめ**。「WCAG を検証できる」としか言っていない
- 実物74件を測ると**2つの流派**があり、**公式サンプルは分布の外**にある。手本にすべきは実物の中央値
- 仕様どおりに書くと壊れる箇所が7件。**うち6件は無警告・exit 0**
- 実装の仕様準拠は**機械判定できる**。決定的チェッカは誤検出ゼロ、視覚 judge も判定可能な範囲で全問正解
- そして judge は**判定できない項目に「分からない」と答えた**。それは設計でそう作ったから

**一番危険なのは、できていないのにできているように見える系です。** エラーも出ず、CI も緑で、出力は自信に満ちている。

「分からない」と言える設計は、機能を減らしているように見えて、**信頼できる範囲を確定させています**。範囲が確定していないものは、そもそも使えません。
