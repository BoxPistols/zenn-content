## TL;DR

Claude Codeはフックを実行するたびに、その所要時間`durationMs`をセッションログに書いています。既に手元にあるそのデータを読んで、どのフックが何分ぶんループを止めたかを出すツールを作りました。

https://github.com/BoxPistols/claude-hook-audit

ラッパーを仕込む必要も、計測のためにフックを再実行する必要もありません。Python 3.9以上、依存ゼロ、MIT。

```
/plugin marketplace add BoxPistols/claude-hook-audit
/plugin install hook-audit@claude-hook-audit
```

記事の本題は、作った道具そのものより、公開したあとで自分の計測が3つ間違っていたと分かった話です。計測ツールを作るなら、その計測自体をどう確かめるかという問題から逃げられません。

## 1回300msのフックは「速い」のか

きっかけは、セッションがなんとなく重いという感覚でした。

フックの速さを見るとき、普通は1回あたりの時間を見ます。2秒を超えたら警告、といった基準です。手元のステータス表示フックは1回296msでしたから、どの基準でも速い部類に入ります。

ところがこのフックは`PreToolUse`に付いていました。ツール呼び出しのたびに発火します。7.8日ぶんのログを数えると、4,644回発火していました。

```
12.7分
```

同じものが`PostToolUse`にも付いていたので、合わせて25分。1週間で25分、ループが止まっていた計算になります。1回296msという数字だけを見ていると、ここには辿り着けません。

必要なのは1回あたりの上限ではなく、発火回数を掛けた合計で並べ替えることでした。

## 既にあるログから測る

フックの計測には先行例があります。`settings.json`の各コマンドの前にラッパーを挟んでログを溜める方式と、フックを直接`--iterations`回実行して測る方式です。

前者は設定を書き換えてからデータが溜まるのを待つ必要があり、後者は実際の発火頻度を反映しません。どちらも「これから測る」道具です。

一方、Claude Codeは`~/.claude/projects/`配下のセッションログに、フック実行の記録を最初から書いています。

```json
{
  "type": "attachment",
  "attachment": {
    "type": "hook_success",
    "hookEvent": "PreToolUse",
    "command": "/path/to/hook",
    "durationMs": 296
  }
}
```

タイムアウトしたときは`timedOut`と`timeoutMs`も入ります。つまり、今日この瞬間に1週間ぶんの答えが出せます。これを読むだけの道具にしました。

出力はこうなります。

```
Window: 63 sessions + 168 subagent transcripts, 7.8 days

Blocking hooks held up the main session for at least 27.7 minutes over this window
  (10 of 15 observed event/hook pairs block).

BLOCKING  (main = time the main session spent waiting, summed over its runs)
      main    runs    median       p95        max  event
     12.7m    4644     296ms    1164ms     9045ms  PreToolUse
  *         [status line updater]
```

処方は単純です。判定するフック(検査・ゲート・書き込み前の確認)はブロックする必要があるのでそのままにします。知らせるだけのフック(ステータス表示・通知)は`"async": true`にします。全イベントで動いたまま、待ち時間だけ消えます。matcherを削る方法より副作用が小さく、表示の粒度を失いません。

手元の2件はどちらも後者でした。asyncにして、表示は1つも失わずに25分が消えました。

## 公開してから、自分の数字を数え直した

ここまでで道具としては動いていました。公開もしました。そのあとで、レビューを受けて自分の計測を実データで数え直したところ、3つ間違っていました。どれも出力される数字そのものが変わるものです。

### 1. 数えていた失敗の型が存在しなかった

エラーを数える節を作っていました。`hook_non_blocking_error`と`hook_error_during_execution`という2つの型を集計する実装です。

手元のログにある10,016件の記録を型ごとに数えました(以下、数値はこの記事を書いた時点のものです)。

| 型 | 件数 |
|---|---|
| hook_success | 9,843 |
| hook_blocking_error | 166 |
| hook_cancelled | 6 |
| hook_additional_context | 1 |

集計対象にしていた2つの型は、1件も存在しませんでした。実在するのは`hook_blocking_error`で、こちらは数えていませんでした。エラーの節は最初から到達不能なコードだったことになります。

この型には少し厄介な性質があります。`command`フィールドも`durationMs`もありません。どのフックの記録なのかを示す情報が、一見どこにもない。

ただしメッセージ本文の先頭が`[コマンド]: 内容`という形になっていました。166件すべてでこの形から復元できたので、そこから引くようにしました。所要時間が無い記録も行として出します。時間がゼロに見えるフックが、書き込みのたびに再試行を発生させていることがあるためです。

### 2. サブエージェントの実行を待ち時間に足していた

所要時間を持つ記録は9,849件で、そのうち4,761件はサブエージェント内で実行されたものでした。半分近くになります。

サブエージェントのフックは、そのサブエージェントを止めます。ただし利用者を待たせてはいません。サブエージェントは互いに、そしてメインのループと並行して走るからです。

所要時間を単純に足すと90.1分になります。一方、記録のタイムスタンプから「いずれかのフックが実行中だった実時間」を求めると67.9分でした。単純和は3割ぶん、起きていない待ち時間を記述していたことになります。

影響は均一ではありません。冒頭で挙げた2件も、実行の約半分がサブエージェント内でした。「週25分ループが止まっている」という話の半分は、実際には並行して走っていたものです。

行ごとに分けて出し、合計にはメインぶんだけを入れるようにしました。

### 3. 合計が実測より28%低かった

合計を`発火回数 × 中央値`で求めていました。全件の中央値を出して、件数を掛ける。

この推定は、中央値より上の標本を全部捨てます。フックの所要時間のように右に裾を引く分布では、その捨てた部分が効きます。

手元のデータで両方を出すと、実測和が90.1分に対して`発火回数 × 中央値`は64.8分でした。28.2%低い。影響の大きい2件に限ると35%低く出ていました。

標本は全部手元にあります。正確な和を取るほうが計算も安いので、実測和に変えました。

## 記録側の仕様で引っかかった点

計測の定義とは別に、記録の読み方でも3つ引っかかりました。いずれも「実行1件を、それを設定したフックに結びつける」ところで効きます。ここが外れると、asyncなのにブロックとして数える、timeoutが設定済みなのに未設定として警告する、といった形で出力が壊れます。

### statusMessageがcommand欄に入る

フックの設定には`statusMessage`という項目があり、実行中に表示する文言を指定できます。

```json
{
  "command": "/usr/bin/python3 \"$HOME/hooks/no-ai-signature.py\"",
  "timeout": 10,
  "statusMessage": "署名と絵文字の検査中"
}
```

このとき、ログの`command`フィールドに入るのはコマンド文字列ではなく`署名と絵文字の検査中`のほうです。

コマンド文字列だけで突き合わせていたので、このフックは1つなのにレポートに2回出ていました。設定側からは「設定にあるが記録なし」として、ログ側からは「設定に無いのでブロック・タイムアウト未設定と仮定」として。実際には`timeout: 10`が設定済みです。

`statusMessage`も突き合わせのキーに入れて解決しました。

### プラグインのフックは別のファイルに書かれている

プラグインが提供するフックは`settings.json`ではなく、プラグイン自身の`hooks/hooks.json`に書かれています。こちらを読んでいなかったので、プラグイン由来のフックは全部「設定に無い」扱いでした。

インストール済みプラグインの一覧から辿って読むようにしました。後から無効化したプラグインも読みます。無効化前の実行がログに残っているためです。ただし「設定にあるが記録なし」の一覧からは外します。

もう1点、プラグインのコマンドは`${CLAUDE_PLUGIN_ROOT}`が展開済みの形で記録されることがあります。展開後の形でも索引するようにしました。

### timeoutは秒、timeoutMsはミリ秒

`settings.json`の`timeout: 10`に対して、ログには`timeoutMs: 10000`が入ります。単位が違います。

JSON出力で両方を隣に並べていたので、`timeout_s`と`timeout_observed_ms`に分けました。

あわせて、タイムアウトの記録を見ていて気づいたことがあります。

```
durationMs: 19455, timeoutMs: 10000
```

上限10秒に対して、記録された所要時間は19.4秒でした。`durationMs`はタイムアウト時の上限値そのものではなく、上限を超えることもある下限値です。ドキュメントに「上限が入る」と書いていたので直しました。

## テストが効いているかをどう確かめたか

ここまでの修正はすべて数字が変わるものです。テストを書きましたが、テストが全件通過することと、テストが意味を持っていることは別です。

そこで、直した箇所を1つずつ元の実装に戻して、対応するテストが落ちるかを確かめました。`statusMessage`のキー登録を外す、`isSidechain`を無視する、合計を`発火回数 × 中央値`に戻す、といった改変を順に入れます。

1件、通ってしまうものがありました。合計を中央値の推定に戻す改変です。アサーションが別のフィールドを見ていて、そのフィールドは改変の影響を受けていませんでした。アサーションを足して、落ちることを確認しました。

READMEのサンプル出力についても、書式文字列から組み立てた行が記事中のサンプルと一致するかをテストで固定しています。出力の形を変えてREADMEを直し忘れると落ちます。ずれたサンプルは、無いよりも悪いためです。

## レポートを人に渡すとき

このツールの既定の出力には、絶対パス(アカウント名を含む)とコマンド文字列がそのまま出ます。インラインシェルのフックは、設定ファイルに書かれた内容をそのまま持ちます。

用途が「順位を人に見せて相談する」ものなので、`--redact`を用意しました。

```
  *         notify.py busy       ← /usr/bin/python3 "$HOME/hooks/notify.py" busy
            <inline shell>       ← パイプや連結を含むものは中身を出さない
```

スクリプト名と引数だけになります。引数を残すのは、同じスクリプトを引数違いで登録している場合に区別が付かなくなるからです。件数と時間は両モードで同一になるようにしてあります。

なお、GitHubのSecret scanningやPush protectionはトークンの形をした文字列を検出するもので、絶対パスやアカウント名は止めません。このツールが出力するのは後者なので、そこは道具側で面倒を見る必要がありました。

## 限界

記録の形は、Claude Code 2.1.267から2.1.275が書いた約10,000件から読み取ったものです。1台、1人のフック構成ぶんです。別の版では違う形を書く可能性があります。

そのため、知らない型の記録は「知らない型」として、どのフックのものか分からない記録は件数と型名として、それぞれレポートに出します。黙って落として間違った合計を出すよりはましだという判断です。どちらかが出たら、形式が変わったと考えて周辺の数字を見直してください。

もう1つ、合計は下限です。成功して出力が空のフックはログに永続化されないため、そもそも見えません。レポートには「設定にあるが記録が無いフック」の件数を併記しています。ゼロは「使われていない」ではなく「記録が無い」です。

## まとめ

- フックの速さは1回あたりではなく、発火回数を掛けた合計で見る
- その合計には、サブエージェント内の実行を足さない。並行して走るので、足すと起きていない待ち時間になる
- 合計は中央値の推定ではなく実測和で出す。右に裾を引く分布では3割近く変わる
- 計測ツールを作ったら、その計測が何を数えているかを実データで数え直す。存在しない型を数えていることがある
