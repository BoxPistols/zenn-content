---
title: "実装チェックリスト"
---

本章では、これまでの各章で解説した内容を実装時に確認できるチェックリストとしてまとめる。新規開発時のセルフレビュー、コードレビュー、リリース前の最終確認に活用されたい。

## 1. HTML セマンティクス

- [ ] landmark 要素（`<header>`, `<nav>`, `<main>`, `<footer>`）を使用している
- [ ] `<main>` はページ内に 1 つだけ存在する
- [ ] 見出し（`<h1>`〜`<h6>`）がレベルを飛ばさず階層的に使用されている
- [ ] `<h1>` はページ内に 1 つだけ存在する
- [ ] 装飾目的の画像には空の `alt=""` を設定している
- [ ] 情報を伝える画像には内容を適切に説明する `alt` テキストを設定している
- [ ] リスト構造には `<ul>` / `<ol>` / `<dl>` を使用し、`<div>` の羅列で代用していない
- [ ] リンク（`<a>`）とボタン（`<button>`）を用途に応じて使い分けている
- [ ] `<section>` にはアクセシブルな名前（見出しまたは `aria-label`）を付与している
- [ ] 言語属性（`<html lang="ja">`）を正しく設定している
- [ ] `<em>`, `<strong>`, `<time>`, `<abbr>` などのインライン意味要素を適切に使用している

## 2. ARIA

- [ ] ネイティブ HTML 要素で表現できる場合は ARIA を使わない（第一原則）
- [ ] `aria-label` または `aria-labelledby` でインタラクティブ要素にアクセシブルな名前を付与している
- [ ] 補足説明が必要な要素に `aria-describedby` を設定している
- [ ] 動的に更新される領域に `aria-live="polite"` または `aria-live="assertive"` を設定している
- [ ] 開閉状態を持つ要素に `aria-expanded` を設定し、状態変化に応じて値を更新している
- [ ] 表示/非表示を制御する要素に `aria-hidden` を正しく使用している
- [ ] `role` を付与した場合、その role に必要な ARIA プロパティをすべて設定している
- [ ] `aria-current="page"` でナビゲーション内の現在ページを示している
- [ ] カスタムコンポーネントには WAI-ARIA Authoring Practices に準拠した role とキーボード操作を実装している
- [ ] `aria-hidden="true"` をフォーカス可能な要素やその親に設定していない

## 3. フォーカス管理

- [ ] `tabindex="0"` はフォーカス可能にする必要があるカスタム要素にのみ使用している
- [ ] `tabindex` に 1 以上の正の値を使用していない
- [ ] Skip Navigation リンクをページ先頭に設置している
- [ ] モーダルダイアログ内でフォーカストラップを実装している
- [ ] ダイアログを閉じた後、トリガー要素にフォーカスを戻している
- [ ] フォーカスインジケーター（`:focus-visible`）が視認可能な状態で表示されている
- [ ] `outline: none` でフォーカスインジケーターを削除していない（代替スタイルがある場合を除く）
- [ ] キーボードのみで全機能を操作可能である
- [ ] SPA のページ遷移後にフォーカス位置が適切にリセットされている
- [ ] フォーカス順序が視覚的なレイアウト順序と一致している

## 4. Dialog

- [ ] ネイティブの `<dialog>` 要素を使用している（または同等のアクセシビリティを実装している）
- [ ] モーダルは `showModal()` で開き、背景のスクロールとインタラクションを抑制している
- [ ] Escape キーでダイアログを閉じることができる
- [ ] 閉じるボタン（`<button>`）がダイアログ内に配置されている
- [ ] ダイアログが開いたとき、ダイアログ内の適切な要素にフォーカスが移動している
- [ ] ダイアログを閉じたとき、トリガー要素にフォーカスが戻っている
- [ ] `aria-labelledby` でダイアログのタイトルを関連付けている
- [ ] 確認ダイアログの破壊的アクション（削除など）のボタンにはデフォルトフォーカスを当てていない
- [ ] Dialog でなくても実現できる場合（トースト、インラインメッセージ等）は Dialog を使っていない
- [ ] 背景の `::backdrop` に適切な不透明度を設定し、モーダルであることが視覚的に明確である

## 5. Snackbar / Toast

- [ ] `aria-live="polite"` を設定した領域にメッセージを挿入している
- [ ] 重大なエラーには `role="alert"`（`aria-live="assertive"`）を使用している
- [ ] 自動消去のタイミングが短すぎない（最低 5 秒以上を目安とする）
- [ ] ユーザーがホバーまたはフォーカスしている間は自動消去を一時停止している
- [ ] 手動で閉じるボタンを提供している
- [ ] 画面下部や上部など、レイアウトを崩さない位置に `position: fixed` で配置している
- [ ] 複数のトーストが同時に表示される場合、スタック表示で情報が欠落しない
- [ ] 色だけでなくアイコンやテキストでも状態（成功・エラー・情報）を伝えている
- [ ] アクションボタン（「元に戻す」等）がある場合、キーボードでアクセス可能である

## 6. Form

- [ ] すべての入力要素に `<label>` を関連付けている（`htmlFor` / `id` の対応）
- [ ] 関連するラジオボタンやチェックボックスを `<fieldset>` と `<legend>` でグループ化している
- [ ] 必須フィールドに `required` 属性と `aria-required="true"` を設定している
- [ ] 必須であることを色だけでなくテキスト（「必須」表記や `*`）でも示している
- [ ] エラーメッセージを `aria-describedby` で入力要素に関連付けている
- [ ] エラー発生時に `aria-invalid="true"` を設定している
- [ ] エラーメッセージは問題の内容と修正方法を具体的に記載している
- [ ] フォーム送信後のエラーサマリーをフォーム先頭に表示し、フォーカスを移動している
- [ ] `autocomplete` 属性を適切に設定している（`name`, `email`, `tel` 等）
- [ ] バリデーションはサーバーサイドでも行い、クライアントサイドのみに依存していない
- [ ] プレースホルダーをラベルの代替として使用していない

## 7. Table

- [ ] データテーブルに `<caption>` でテーブルの概要を提供している
- [ ] ヘッダーセルに `<th>` を使用し、`scope="col"` または `scope="row"` を設定している
- [ ] レイアウト目的で `<table>` を使用していない
- [ ] テーブルのネスト（テーブル内テーブル）を行っていない
- [ ] 横幅が画面に収まらない場合、`overflow-x: auto` の水平スクロールコンテナで囲んでいる
- [ ] スクロールコンテナに `tabindex="0"` と `role="region"` と `aria-label` を設定している
- [ ] モバイル表示でテーブルが崩れないレスポンシブ対応を実施している
- [ ] 複雑な結合セル（`colspan` / `rowspan`）がある場合、`headers` 属性で関連付けている
- [ ] ソート可能なテーブルでは `aria-sort` でソート状態を示している

## 8. ダークパターン

- [ ] Confirmshaming（断ることを恥ずかしくさせる文言）を使用していない
- [ ] 「同意する」と「拒否する」のボタンを同等の視認性で提供している
- [ ] Cookie バナーに「すべて拒否する」ボタンを配置している
- [ ] Cookie の使用目的を具体的に明記している
- [ ] オプション商品やサービスのチェックボックスはデフォルト OFF にしている
- [ ] 解約・退会フローが登録フローと同等の容易さで完了できる
- [ ] 無料トライアル終了前にリマインド通知を送信している
- [ ] 価格表示は全プラン同一単位（月額 or 年額）で比較可能にしている
- [ ] 二重否定やあいまいな表現をフォームの質問文に使用していない
- [ ] 購入プロセスの最初の段階から送料・手数料を含む総額を表示している
- [ ] 通知の許可はユーザーが価値を理解した適切なタイミングで要求している
- [ ] 無限スクロールを使用している場合、フッターへのアクセス手段を別途提供している

## 9. パフォーマンス

- [ ] Core Web Vitals が以下の基準を満たしている
  - [ ] LCP（Largest Contentful Paint）: 2.5 秒以内
  - [ ] INP（Interaction to Next Paint）: 200ms 以内
  - [ ] CLS（Cumulative Layout Shift）: 0.1 以下
- [ ] JavaScript の合計バンドルサイズに上限（パフォーマンスバジェット）を設定している
- [ ] 不要なライブラリを含めていない（ネイティブ API で代替可能か確認済み）
- [ ] 重いコンポーネントは `lazy()` + `Suspense` で動的インポートしている
- [ ] 画像に `loading="lazy"` と適切な `width` / `height` を設定している
- [ ] 次世代フォーマット（WebP / AVIF）で画像を配信している
- [ ] サードパーティスクリプトの転送サイズとブロック時間を定期的に監査している
- [ ] Content Security Policy（CSP）でスクリプトの出所を制限している
- [ ] 収集するユーザーデータが必要最小限であることを確認している
- [ ] `prefers-reduced-motion: reduce` でアニメーションを抑制する対応を実施している
- [ ] `prefers-color-scheme: dark` でダークモードに対応している
- [ ] サードパーティスクリプトが送信するデータの送信先ドメインを把握している

## 活用方法

本チェックリストは以下の場面での活用を想定している。

| 場面 | 対象カテゴリ | 頻度 |
|------|------------|------|
| コンポーネント実装時 | 該当するカテゴリ | 都度 |
| コードレビュー時 | レビュー対象に関連するカテゴリ | 都度 |
| リリース前の最終確認 | 全カテゴリ | リリースごと |
| 定期監査 | パフォーマンス、ダークパターン | 四半期ごと |

### 段階的な導入の指針

すべての項目を一度に対応する必要はない。以下の優先度を参考に段階的に導入し、チームの習慣として定着させることが重要である。

**優先度: 高（法的リスク・基本的人権に関わる項目）**

- landmark 要素と見出し階層の適切な使用
- フォームのラベル関連付けとエラーメッセージ
- キーボード操作の完全対応
- ダークパターンの排除（Cookie バナー、解約フロー）

**優先度: 中（ユーザー体験に大きく影響する項目）**

- ARIA 属性の適切な使用
- Dialog のフォーカス管理
- Core Web Vitals の基準達成
- 画像の代替テキストと最適化

**優先度: 低（品質向上に寄与するが段階的に対応可能な項目）**

- Snackbar / Toast の細かい制御
- テーブルのソート状態表示
- パフォーマンスバジェットの自動化
- サードパーティスクリプトの定期監査

:::message
本チェックリストは固定的なものではない。WCAG のバージョンアップ、ブラウザの新機能追加、法規制の変更に応じて定期的に見直し、プロジェクトの要件に合わせてカスタマイズされたい。
:::
