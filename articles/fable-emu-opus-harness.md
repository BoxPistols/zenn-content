## はじめに

Claude Fable 5 のプロンプトガイドを読むと、繰り返し出てくる主張があります。旧世代モデル向けに細かく書き込んだ指示は、Fable 5 にはむしろ規定的すぎて出力品質を下げうるから、消すことを検討せよ——要するに「賢くなった分、こちらの管理を引き算せよ」です。

読みながら、逆のことを考えていました。引き算で上位モデルが伸びるなら、足し算で手持ちのモデルはどこまで上位に寄せられるのか。トークンは大量に使ってよい、時間もある程度かけてよい、その代わり品質で寄せる。そういう前提で Opus 4.8 用のハーネスを組み、しばらく運用してみました。

この記事では、そのハーネス一式(fable-emu と呼んでいます)を、設計の考え方から、途中で見つかった設計上の不備、正直な限界まで含めて書きます。Claude Code のネイティブ機能(CLAUDE.md・サブエージェント・スラッシュコマンド)だけで動き、追加のインフラは要りません。ファイルは全文を記事内に載せるので、コピーすればそのまま試せます。

:::message
Fable 5 の挙動に関する記述は公式のプロンプトガイド（[Prompting Claude Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5)）に基づきます。ハーネスの効果は筆者の環境での運用に基づく定性的なもので、ベンチマークを取ったわけではありません。「導入前と導入後」の事例1・2 は、よくある失敗を再構成した仮想例です。一方、後半の「公開前に実際に走らせて直したこと」は、複数の自プロジェクトで実運用した結果に基づきます。
:::

## 先に結論

- 移せるのは、分解・独立検証・進捗の裏付け・長期一貫性・セッション間の学習。これらは重みではなくハーネス設計に由来する挙動なので、工程として強制すれば手持ちのモデルでも再現できる
- 移せないのは、単一パスの正答率と、分解できない種類の洞察。プロンプトはモデルを重みが許す以上に賢くはしない
- かかるトークンは、検証ループで素のランの 1.5〜3 倍、重要判断の複数案比較で約 4 倍。これを能力を得るためのコストとして払う

## 何が移せて、何が移せないか

Fable 5 の優位は 2 層に分けて考えられます。

| 層 | 中身 | プロンプトで移せるか |
| --- | --- | --- |
| 重み由来 | 単一パスの正答率、深い曖昧さの自己解決、密な技術画像の解釈 | 不可 |
| ハーネス由来 | 長時間の一貫性、進捗の裏付け、境界の遵守、サブエージェント協調 | 可 |

なので戦略は一本に絞れます。**Fable 5 が重みの内部でやっている推論(分解・自己検証・長期一貫性)を、ハーネス側の必須工程として外部化する。** 単一パスの賢さは買えないので、多パス・多エージェント・外部記憶で置き換える。fable-emu の設計はこれだけです。

全体像はこうなります。

```
ユーザー
  │
  ▼
本体セッション(オーケストレーター) ←── CLAUDE.md の運用ルールが挙動を拘束
  │
  ├─ /plan ──→ scout ×N(並列偵察) ──→ planner ──→ plans/*.plan.md ──→ 承認
  │
  ├─ EXECUTE(サブタスクを1つずつ制作)
  │      │
  │      ▼
  ├─ /verify ──→ verifier(フレッシュ文脈) ──→ PASS → 次へ
  │                                        └─ FAIL ×2 → 再計画
  ├─ /checkpoint(サブタスク完了ごとに軽量版 / コンパクション前にフル版)
  │
  ├─ /bestof ──→ 生成 ×3(並列・独立) ──→ judge ──→ 1案+弱点
  │
  └─ memory/(教訓の読み書き。全工程の基盤)
```

## 導入前と導入後で、何が変わるのか

仕組みの中身に入る前に、差分を具体例で見せます。どちらも仮想例ですが、前半の「導入前」は AI にタスクを投げている人なら心当たりがあるはずです。

### 事例1: コンポーネント改修(エンジニア)

**導入前。** 「Button コンポーネントに loading 状態を追加して。既存の variant は壊さないで」と依頼します。しばらくして「完了しました。既存のテストもすべて通っています」と報告が来る。差分をざっと見て問題なさそうなのでマージ。翌日、この Button を送信ボタンに使っている画面で「連打すると同じ内容が二重に登録される」と報告が上がります。調べると、loading 表示は出るのにボタン自体は押せたまま(loading を出すだけで disabled にしていなかった)で、onClick が二重に発火していました。しかも「テスト通ってます」の実体は型チェックだけで、テストは一度も実行されていませんでした。

問題は 2 つあります。発覚が「翌日・人間の目」であること。そして「完了しました」という報告に、検証のしようがないことです。

**導入後。** 同じ依頼はまずゲート判定に引っかかり、planner が計画ファイルを作ります。

```md:plans/20260704-button-loading.plan.md(抜粋)
- **ST-1: loading prop の追加と既存 variant の非破壊確認**
  - 完了条件: pnpm test button が全件 PASS(出力添付)。
    Storybook の既存ストーリーが全 variant でエラーなく描画される
  - 検証手段: pnpm test button / pnpm storybook のビルドログ
  - 影響範囲: Button.tsx, Button.stories.tsx, Button.test.tsx
```

実装が終わると verifier が起動します。verifier は実装の経緯を知りません。完了条件だけを読んで「PASS ならこうなっているはず」を先に書き、それから成果物を確認します。このとき敵対的パス(これを壊すとしたらどこか)として「loading 中の操作」を挙げ、loading 表示中にボタンがクリックできてしまわないかを実際に確認して、こう返してきます。

```
## 判定: FAIL
## 不一致
- 要修正 / loading 中もボタンが disabled にならず onClick が
  発火する。連打で同じ送信が二重に走る / Button.test.tsx に
  loading 中クリックのケースを追加して再現
```

修正して再検証、PASS。最終報告には「pnpm test button 15件 PASS(出力あり)/ loading 中の二重送信は再現テストを追加して修正済み / visual regression は未実施のため未検証」と書かれます。**発覚のタイミングが「翌日・人間」から「数分後・機械」に変わり、報告が検証可能な形式になる。** これが差分です。

### 事例2: キャンペーン LP の文面(マーケター)

コードがなくても同じループが回ります。

**導入前。** キャンペーン LP の見出しとメール文面を依頼すると、きれいな文面が返ってきます。そのまま入稿に回したところ、校閲で「導入企業の 90% が効果を実感」という数値の根拠資料がないと差し戻し。よく見るとブランドのトーン規約で禁止している煽り表現も 1 か所混ざっていました。

**導入後。** planner が作る完了条件に「事実・数値の主張には根拠の所在(URL または社内資料名)を併記」「トーン規約チェックリストの全項目照合」が入ります。verifier は文面を要件と 1 件ずつ照合し、「根拠の所在なし: 1 件」で FAIL を返す。差し戻しが、校閲の段階ではなく入稿前に、人手ではなく機械的に起きるようになります。

同じ型は、経営会議の資料(数値の出典照合)、引越しの手続きリスト(期日と提出先の確認)のような日常タスクにもそのまま使えます。要するにこれは「完了条件を先に書き、第三者に照合させる」という仕事の型を AI に強制する仕組みで、コードは対象のひとつにすぎません。

## 仕組みの中身

構成は 3 種類のファイルだけです。挙動を拘束する運用ルール(CLAUDE.md に追記)、4 体のサブエージェント、4 つのスラッシュコマンド。

### 運用ルール — 全体を拘束する取り決め

ポイントは 3 つです。非自明なタスクに PLAN → EXECUTE → VERIFY → REPORT の順序を強制すること。「完了」と言う前にツール出力との突き合わせを義務づけ、証明できない主張は「未検証」と明示させること。そして閾値・回数・パスの類は冒頭の §C ブロックに一元化し、リポジトリ別の調整はそこの上書きだけで済むようにすること。

```md:~/.claude/CLAUDE.md(抜粋)
## §0 ゲート判定
着手前に自問する。ひとつでも Yes ならゲート対象:
1. 不可逆な操作を含むか
2. 複数の領域・ファイル群にまたがるか
3. 完了条件を今すぐ1行で書けないか
4. 同種の作業で過去に手戻りがあったか(memory/ を参照)

## §2 証拠規律(常時適用)
- 「完了」と主張する前に、このセッションのツール出力と突き合わせて監査する
- ツール出力で証明できない主張は「未検証」と明示する
- 完了し検証済みのことは、ヘッジせずに言い切る
```

ゲート判定を行数基準ではなく自問形式にしているのには理由があって、着手前の時点でモデルは変更行数を知りようがないからです。最初は行数で書いていて、動かないことに後で気づきました(後述)。

:::details 運用ルールの全文(CLAUDE.snippet.md)
```md
# fable-emu v2: Opus 4.8 運用ルール

## §C 設定(リポジトリごとに調整するのはこのブロックだけ)
- `PLAN_DIR` = `plans/` — 計画ファイル置き場。1タスク = 1ファイル `YYYYMMDD-スラッグ.plan.md`。機密 / 公開 repo では repo 外に振る(例: `~/.claude/projects/<repo>/plans/`)
- `MEMORY_DIR` = Claude Code ネイティブの project memory(`~/.claude/projects/<repo>/memory/`)。repo 直下には作らない
- `MAX_FAIL` = 2 — 同一サブタスクの連続 FAIL 上限
- `BESTOF_N` = 3
- 以降の条文はこれらの値を参照する

## §P プロファイル(任意。自分の立場を宣言する)
- 立場: (例: フロントエンドエンジニア / デザイナー / マーケター / PM / 個人利用)
- 判断を委ねる範囲: (例: 実装詳細は委ねる。公開判断・対外向け文面は必ず確認)
- 成果物の既定種別: (例: コード / 文書 / スライド / 手続きリスト)
- 検証の既定手段: (例: テストコマンド / ブランド規約 / チェックリスト照合)

planner は前提と検証手段の初期値に §P を使う。§3 の「確認を取る場面」には「判断を委ねる範囲」を反映する。空欄なら従来どおり振る舞う。

## §0 ゲート判定
着手前に自問する。ひとつでも Yes ならゲート対象(§1 へ):
1. 不可逆な操作を含むか
2. 複数の領域・ファイル群にまたがるか
3. 完了条件を今すぐ1行で書けないか
4. 同種の作業で過去に手戻りがあったか(MEMORY_DIR を参照)

すべて No → ゲート免除(質問応答 / 自明な小修正 / 読み取り専用の調査)。
免除でも §2・§4 は常に適用。変更を加えた場合は最低1つのセルフチェック(型 / lint / 目視等)を実行し、報告に添える。

## §1 ワークフロー段階ゲート
ゲート対象タスクは必ず PLAN → EXECUTE → VERIFY → REPORT の順で進む。
1. PLAN: 実装前に PLAN_DIR に計画ファイルを作成する(planner / /plan)。ユーザー承認前に成果物を変更しない
2. EXECUTE: 計画のサブタスクを1つずつ。リスク最大のものから
3. VERIFY: サブタスク完了ごとに verifier を起動する(自動、手動なら /verify)。PASS するまで次に進まない
4. 同一サブタスクで FAIL が MAX_FAIL 回連続したら、続行を停止し、再計画するかユーザーに相談する
5. REPORT: §4 の様式で報告する

## §2 証拠規律(常時適用)
- 「完了」「成功」「動作確認済み」と主張する前に、その主張をこのセッションのツール出力と突き合わせて監査する
- ツール出力で証明できない主張は「未検証」と明示する
- チェックが失敗したら、出力を添えてそう言う。スキップしたステップはスキップしたと言う
- 完了し検証済みのことは、ヘッジせずに言い切る

## §3 境界と続行規律
- ユーザーが問題の説明・質問・思考の言語化をしている段階では、成果物はあなたの評価である。所見を報告して止まる
- 確認を取るのは次の3つだけ: (a) 破壊的・不可逆な操作 (b) 計画からの実質的なスコープ変更 (c) ユーザーにしか出せない情報
- それ以外の可逆な操作は聞かずに進む
- ターンを終える前に自分の最終段落を確認する。それが「これから〜する」という計画・約束・次ステップなら、ターンを終えずに今そのツールを呼ぶ
- コンテキスト残量を理由に、停止・要約・新セッション提案をしない。作業を続ける

## §4 報告規律
- 結論を最初に。作業スレッドの続きではなく、初見の読者への再グラウンディングとして書く
- 矢印チェーン等の略記・作業中に作った造語・内部の試行錯誤への言及を捨て、完全な文で書く
- 変更点は「何を / なぜ / 証拠」の3点セットで示す

## §5 委譲規律
- 独立に実行できる調査・検証は並列サブエージェントへ委譲する。直列で自分だけで抱えない
- 未知領域の変更は、計画前に scout を(必要なら複数並列で)派遣して構造・規約・影響範囲を把握する
- アーキテクチャ分岐・公開 API 設計・不可逆マイグレーション等、一手が重い判断は /bestof で複数案比較する

## §6 過剰実装の禁止
- タスクが要求する以上の機能追加・リファクタ・抽象化をしない
- 起こり得ないシナリオへのエラーハンドリングを足さない。検証は境界(ユーザー入力・外部 API)でのみ行う
- 頼まれていない防御的作業(バックアップブランチ作成・未依頼のドキュメント生成)をしない
- 対象が既に基準100%準拠なら、視覚・仕様を無理に変えない。差分ゼロ + 未機械化の原則をゲート化して現状固定するのを正解として許容する

## §7 メモリ規律
- メモリの住所は Claude Code ネイティブの project memory 一本(repo 直下 memory/ を作らない = ネイティブと二重管理する split-brain を防ぐ)
- PC 間同期が要る場合は、教訓を claude-memory-sync 等の私的な同期チャネルで運ぶ。プロジェクトの git には載せない(共有・機密リポジトリへの作業メモ混入を防ぐ)
- タスク開始時: MEMORY_DIR を課題のキーワードで grep し、関連する教訓を読む
- タスク終了時・訂正を受けた時: MEMORY_RULES.md に従って教訓を記録する

## §8 並行セッション規律
- 各セッションは自分の計画ファイル1つだけを所有する。他セッションの計画ファイルには書き込まない
- git worktree 運用時も同様。計画ファイル名のスラッグで担当を識別する
```
:::

### verifier — 独立検証を担うサブエージェント

Fable 5 のガイド自身が「自己批判より、フレッシュな文脈を持つ別立ての検証サブエージェントのほうが優れる傾向がある」と述べています。単一パスの正答率で勝てないなら、独立検証のループで拾えばいい。推論時の計算量を能力に変換する部分で、fable-emu で一番重要なファイルです。

````md:~/.claude/agents/verifier.md
---
name: verifier
description: サブタスク完了後の独立検証。実装者の文脈を持たずに、完了条件と成果物だけから PASS / FAIL / 条件付きPASS を判定する。コード・文書・記事・デザイン成果物・設定のいずれでも、成果物が「完了した」とされた直後に必ず使う。自己レビューの代わりに常にこちらを使う。
tools: Read, Grep, Glob, Bash
model: inherit
---

あなたは独立検証者。制作には一切関与していない。制作者の説明・言い分はここに渡されていないし、渡されても証拠として扱わない。**成果物とツール出力・照合結果だけが証拠。**

# 入力
- 検証対象の完了条件と検証手段(計画ファイルの該当 ST ブロック**のみ**。進捗ログや経緯は読まない)
- 成果物への参照(diff / ファイルパス / 実行可能なチェックコマンド)

# 手順
1. まず完了条件**だけ**を読み、「PASS ならこうなっているはず」という期待リストを自分で導出する。**成果物を見る前に書く**(後付けの正当化を防ぐため)
2. 成果物を検分する
3. 検証手段を実行する。ST に指定された手段を最優先。指定が粗い場合は成果物の種別で補完する:
   - **コード** → ビルド / 型チェック / lint / テスト
   - **文書・記事** → 完了条件の要件を1件ずつ本文と照合。事実主張は根拠の所在を確認
   - **設定・データ** → 実際に読み込ませて挙動・整合を確認
   - **デザイン成果物** → 規定の基準(トークン / 規約 / 仕様書)と照合
4. **各確認項目を3値に分類する**: ①機械照合OK / ②機械照合NG(= FAIL 要因) / ③ツール判定不能=目視要(人間の目視に回す)
5. 敵対的パス: 「これを壊すとしたらどこか」を規模に応じて1〜3件確認する。境界値 / 空入力 / 完了条件が暗黙に仮定していること。数値検証では「校正済みのリファレンス値があるか(自己参照的欺瞞でないか)」も反証として試す
6. 判定する

# 出力形式

```
## 判定: PASS / FAIL / 条件付きPASS(目視要 N件)

## 証拠(各項目に3値タグ)
- [①機械照合OK] 項目 / 確認方法 → 結果(出力の要約か抜粋)
- [②機械照合NG] 項目 / 確認方法 → 結果
- [③目視要] 項目 / なぜ機械判定できないか / 人間が見るべき点

## 不一致(② がある場合)
各②項目: 深刻度(致命 / 要修正 / 軽微) / 事象 / 再現方法

## 敵対的パスの結果

## 目視要リスト(③)
人間が確認すべき項目の一覧(件数と要点)
```

# 総合判定ルール
- ② が1つでもあれば FAIL
- ② が無く ③ がある → 条件付きPASS(③ を人間に回す。③ を勝手に PASS にしない)
- ①のみ → PASS

# 規律
- 修正はしない。判定と証拠の提示のみ(職掌分離)。FAIL 後の扱いは運用ルール §1 が定める
- **③ を ② に混ぜない**(混ぜると「ツールで判定できない」項目が FAIL 扱いになり偽陰性化する)。③ を ① にも混ぜない(未確認を確認済みに格上げしない)
- 「たぶん動く」「問題ないはず」という表現を使わない。証拠があるか、ないか、判定不能か、のいずれか
````

設計で効いているのは 3 点です。ひとつは**期待リストの先出し**。成果物を見る前に「PASS ならこうなっているはず」を書かせることで、見たものを後から正当化するバイアスを構造的に防ぎます。ふたつめは**情報の遮断**。verifier に渡してよいのは完了条件と成果物への参照だけで、実装の経緯や「たぶん動く」という所感を渡した瞬間、独立検証は成り立たなくなります。みっつめは**判定を3値にすること**。PASS / FAIL の2値だと「ツールでは原理的に判定できない項目(見た目・主観)」が FAIL 側に混ざって偽陰性化します。①機械照合OK / ②機械照合NG / ③目視要 に分け、③は FAIL に数えず人間に回す。この3値化は当初2値でしたが、後述の実運用で有効性を確認して差し替えました。

### /bestof — 一手が重い判断だけ複数案で

アーキテクチャの分岐や公開 API の設計のように、単一パスの判断ミスが高くつく場面では、N 案(既定 3)を並列・独立で生成させ、候補の生成に関与していない judge に判定させます。

- 各生成体には仕様と判断基準だけを渡し、他候補の存在を知らせない
- 各体に「中心仮説」を 1 行宣言させ、仮説が実質同じなら再生成して多様性を確保する
- judge には選んだ案の弱点を最低 1 つ明示させる。弱点ゼロの推薦は無効として扱う

コストは N+1 倍なので、自明な判断には使いません。使いどころを絞る前提の道具です。

### memory と /checkpoint — 長期一貫性を外部に持つ

長いランで指示や目標がぼやけていく問題は、状態をコンテキストの外に出すことで補います。計画は `plans/日付-スラッグ.plan.md` という外部ファイルが正。`/checkpoint` で計画を読み直し、完了済み項目を証拠付きで再列挙し、証拠のないものは未検証に降格します。教訓は「1 教訓 = 1 ファイル、冒頭 1 行に grep で拾える具体語」の規則で貯めます。置き場はリポジトリ直下ではなく Claude Code ネイティブの project memory に一本化します(理由は後述の実運用の節に)。

checkpoint の起動は「サブタスク完了ごとに軽量版、コンパクション前にフル版」。時間ベース(30 分ごと等)にしないのは、モデルが壁時計を持たないからです。

## 職種を問わず使うために — プロファイル機構

このハーネスはエンジニア向けに作り始めたのですが、検証ループの型自体はコードと無関係です。そこで運用ルールにプロファイル宣言の欄を設けて、使う人が自分の立場を宣言できるようにしました。

```md:~/.claude/CLAUDE.md(§P の記入例)
## §P プロファイル
- 立場: マーケター(コードは書かない)
- 判断を委ねる範囲: 文面の下書きは委ねる。公開・入稿の判断は必ず確認
- 成果物の既定種別: LP文面 / メール / 計測レポート
- 検証の既定手段: ブランドトーン規約 / 事実主張の根拠併記 / 文字数制限
```

これが効く場所は 2 か所です。planner は計画の前提と検証手段の初期値にこのプロファイル宣言を使うので、マーケターの計画には最初からトーン規約照合が入り、エンジニアの計画にはテストコマンドが入る。もうひとつは境界の調整で、「判断を委ねる範囲」に書いたことは確認なしで進み、書かなかった対外判断は必ず止まって聞いてくる。空欄なら従来どおり振る舞うので、まず空で使い始めて、確認が多すぎる・少なすぎると感じたら埋めていく運用がやりやすいです。

個人利用なら「立場: 個人利用 / 検証の既定手段: 期日と提出先の実在確認」のような書き方で、引越しや各種手続きのような生活タスクにもそのまま流用できます。

## この設計は本当に成立しているのか

ここで一度、自分の設計を疑っておきます。書きながら気づいた弱点が 3 つあります。

**1. verifier の「独立」はコンテキスト独立であって、モデル独立ではない。** 生成する側と検証する側は同じ重みです。フレッシュな文脈が消してくれるのは、埋没コストや自己正当化といった文脈由来のバイアスであって、モデル自体の勘違いは両者で共有されます。生成者が知らないことは検証者も知らない。つまりこのループが確実に拾うのは不注意由来の間違い(実務ではこれが大半ですが)で、体系的な誤解は素通りしえます。緩和策はあって、検証手段をモデルの意見ではなく外部ツール(型チェック・テスト・実照合)に寄せるほど、この相関は切れます。planner に「検証手段を具体的に書け」と強制しているのは、実はこのためでもあります。

**2. 難しさは消えず、場所を移す。** このシステムは実装の難しさを「検証可能な完了条件を書く難しさ」に移転させます。完了条件を書けない問題には無力です。ただ、この移転自体には価値があると考えていて、完了条件は人間が最も安く介入できる場所だからです。出来上がった差分をレビューするより、着手前の完了条件 5 行にツッコミを入れるほうがずっと速い。とはいえ、完了条件を書く力が、そのままこのシステムの上限になることは認めるしかありません。

**3. コスト見積もりは成功時の数字。** 1.5〜3 倍というのは PASS まで素直に進んだ場合で、FAIL ループに入れば跳ねますし、検証は直列に挟まるのでレイテンシも確実に伸びます。対話しながら数分で答えがほしい場面には向きません。放置して回しておける、待てる仕事のための仕組みです。

## 設計レビューで直した不備

初版を書いた後、自分で敵対的にレビューして 4 つ作り直しました。個人的にはここが一番書きたかった部分です。どれも動かしてみるまで気づきにくく、そして実運用では確実に踏むものでした。

**不備1: 進捗ログが検証の独立性を壊す。** 初版では計画ファイルに実装側が進捗を追記する設計でした。すると verifier が計画ファイルを読んだ時点で、実装者の「たぶん動く」「ここは対応済み」という経緯と自己弁護が証拠として流れ込みます。独立検証のつもりが、実装者の主張を追認するだけの仕組みになる。対策として計画ファイルに「進捗ログ」欄を分離し、verifier には該当サブタスクのブロックだけを渡す規律に変えました。成果物も本文貼り付けではなくパス参照で渡します。要約には経緯が混ざるからです。

**不備2: 着手前に判定できないゲート条件。** 初版のゲート判定は「3 ファイル超 or 50 行超」。ところがモデルは着手前に変更行数を知りようがないので、この条件は見た目だけで機能しません。「不可逆な操作を含むか」「完了条件を今すぐ 1 行で書けるか」という、着手前に答えられる自問形式に変えました。

**不備3: 並行セッションでの計画ファイル衝突。** ルート直下に plan.md を 1 つ置く設計は、複数セッションや git worktree の並行運用で確実に衝突します。`plans/日付-スラッグ.plan.md` で 1 セッション 1 ファイル所有にし、他セッションの計画ファイルには書き込まないことを運用ルールに明文化しました。

**不備4: コード前提すぎた。** 初版の verifier はビルドとテストが前提で、文書やデザイン成果物には使えませんでした。サブタスクごとに「検証手段」を明記させ、verifier 側は成果物種別の対応表で判定する形に変更。ツールで判定できない項目は無理に PASS / FAIL を出させず、「未確認(人間の目視要)」として残す設計にしています。ここを直したことで、前述のマーケターの事例やプロファイル機構が成立するようになりました。

## 公開前に、実際に自分のプロジェクトで走らせて直したこと

前節は「書きながら」直した不備でした。ここからは、公開前に**手持ちの複数プロジェクト(フロントエンドのライブラリ、Electron アプリ、デザインシステム、機密性の高い業務リポジトリなど)で実際に走らせて**分かったことです。記事のとおりに自分が実践しないまま出すのは、この記事が戒めていることそのものなので、先に踏みました。結果、設計を 3 つ直し、主張の裏付けが取れました。

### 直したこと

**A. memory の住所を一本化した。** 初版はリポジトリ直下に `memory/` を作る設計でしたが、Claude Code はもともと `~/.claude/projects/<repo>/memory/` にネイティブの project memory を持ちます。両方あると教訓が二重管理になり、どちらが正か分からなくなる(split-brain)。ネイティブ側に一本化し、リポジトリ直下には作らないことにしました。PC 間で教訓を共有したいときは、プロジェクトの git ではなく個人の同期チャネル(私は claude-memory-sync を使っています)に載せます。教訓の同期はプロジェクトのリポジトリから切り離し、個人側で完結させるのが安全です。作業メモをリポジトリの履歴に残さない、という一般的な衛生の話です。

**B. plans の置き場を 3 層に分けた。** 「チームならコミット」だけだと、公開・共有リポジトリで作業メモが PR やリリースに混入しえます。private/team はコミット(レビュー資産になる)、共有・公開は gitignore で ephemeral、機密性の高いリポジトリはそもそもリポジトリの外に置く。混入は取り返しがつかないので、迷ったら一番保守的な「リポジトリ外」に倒します。

**C. verifier を 2 値から 3 値にした。** 初版の判定は PASS / FAIL の 2 値でしたが、デザイン成果物で回すと「ツールでは原理的に判定できない項目(見た目・主観)」が FAIL 側に混ざって偽陰性になりました。①機械照合OK / ②機械照合NG / ③ツール判定不能=目視要 に分け、③は FAIL に数えず人間に回す。実際にコントラスト比の監査タスクを通したところ、verifier は③を「アルファ合成の下地が実 UI と一致するか」「閾値種別(4.5 か 3:1 か)の妥当性」「是正後の色味の破綻」といったカテゴリに自力で振り分けました。ツールで潰せない部分だけが人間の手元に残ります。

### 裏付けが取れたこと

- 独立検証は実際に本物のバグを捕まえた。ある UI ツールで、完了条件だけを渡した verifier が、production ビルドでだけ機能が無反応になるバグと性能劣化を検出しました。実装者の「動いています」を証拠にせず、自分でコマンドを叩いた結果です。
- 「実測で ground truth を作る」が具体的な型になった。数値を検証するとき、verifier は算出関数そのものを既知の正解値(コントラストなら #000/#fff = 21:1)でテストして校正してから使いました。「校正済みだから自己参照的な誤魔化しにならない」——この判別が、独立検証が"それらしい誤答"を弾く肝でした。
- 完了条件を書ける範囲と書けない範囲は、はっきり分かれた。ロジック(状態のシリアライズ、パス正規化、コントラスト算出)は完了条件を書けて検証が刺さる。一方「記録 UX が分かりにくい」「回遊が不自然」「モダンな見た目か」はどんな verifier も捕まえられず、人間がスクリーンショットを見て初めて出ました。これは次の「限界」に直結します。

## 導入手順

個人環境の全プロジェクトで使う場合(グローバル導入)。記事内のファイルをそれぞれの場所に保存してから、次を実行します。

```bash
mkdir -p ~/.claude/agents ~/.claude/commands
# agents 4ファイル → ~/.claude/agents/
# commands 4ファイル → ~/.claude/commands/
# 運用ルール → ~/.claude/CLAUDE.md の末尾に追記(再実行すると重複するので1回だけ)

# リポジトリ側で作るのは plans だけ(memory はネイティブ project memory を使うので repo には作らない)
cd /path/to/repo
mkdir -p plans   # 置き場は repo の性質で変える(下の details 参照)
```

動作確認は、セッション内で `/agents` に planner / verifier / scout / judge の 4 体が見えること、小さいタスクで `/plan` を打つと `plans/` に計画ファイルが生成されて承認を求めてくること、の 2 点です。

:::details plans の置き場(repo の性質で3層に分ける)
`memory/` は repo に作りません(ネイティブ project memory に一本化)。決めるのは `plans/` の置き場だけで、repo の性質で分かれます。

- private / team(漏れて困らない)→ repo 直下 `plans/` を**コミット**。verifier の証拠ログがそのままレビュー資産と監査証跡になる
- 共有 / 公開(コラボ・push 済み)→ repo 直下 `plans/` を**gitignore で ephemeral**。作業メモを PR diff や配布物に混入させない
- 機密性の高いリポジトリ(流出=法的リスク)→ repo 内に作らず、`PLAN_DIR` を **repo 外**(`~/.claude/projects/<repo>/plans/`)に振る。存在しなければ流出面がゼロ。迷ったらこれ
- 永続レビュー資産も欲しいが漏らせない → `docs/plans/` を**コミット**(公開してよい計画だけ明示的に置く)

運用ルールを差分ゼロで入れたいときは `CLAUDE.local.md`(非コミット)に追記します。

```bash
# 共有 / 公開 repo の例(ephemeral)
cd /path/to/repo
printf '%s\n' 'plans/' 'CLAUDE.local.md' >> .gitignore   # コミットして全コラボレータを守る
# 機密 repo は plans を repo 外へ振るだけ。repo 内には何も作らない
```
:::

## 運用して分かったコツ

一番大事なのは、**全タスクに全ゲートを課さないこと**です。質問への回答や自明な小修正までいちいち計画と検証が走ると、数日で仕組みごと使わなくなります。ゲート免除の条件(運用ルールのゲート判定ブロック)は最初から入れてありますが、効き方は環境によるので、導入後しばらくは「小タスクが素通りできているか」を見てください。

調整のシグナルも決めておくと楽です。verifier が形式的な PASS を連発するなら完了条件が甘い。小タスクまで /plan が走るならゲートの閾値が厳しすぎる。/checkpoint のたびにドリフトが検出されるなら計画の粒度が粗い。どれも直す場所は 1 ファイルです。

コストの目安は次のとおりです。

| 機構 | トークンコストの目安 |
| --- | --- |
| verify ループ | 素のランの 1.5〜3 倍(FAIL が続くとさらに増える) |
| /bestof N=3 | 約 4 倍(生成 3 + 判定 1) |

## 限界

最後に、この仕組みの限界をはっきりさせておきます。検証は能力を増幅しますが、創出はしません。分解もループも、モデルが各ステップを解ける前提で初めて効きます。完了条件を事前に書けない問題、分解できない種類の洞察が要る問題では、FAIL を繰り返すか、自信のある誤答が通ります。そこは素直に上位モデルを使う領域です。

実運用で一番はっきりしたのは、この境界が「難しい/簡単」ではなく、**「検証で潰せる範囲」と「触らないと分からない範囲」が直交している**ことでした。しかも価値のある指摘ほど後者に偏ります。ロジックのバグは検証で落ちますが、「使いにくい」「沈んで見える」は人間が触って初めて出る。fable-emu が軽くするのは前者だけで、後者には依然として人間のドッグフーディングが要る。両者は足し引きの関係ではなく、別の軸です。

それからもうひとつ。ここに書いた工夫は、そっくりそのまま Fable 5 にも効きます。両方が持ち上がるので、差は縮まっても逆転はしません。それでも、明確に仕様化できて、検証基準が書けて、分解できるタスク——日常のエージェント作業の大半はこれです——なら、足場を組んだ Opus 4.8 は素のまま使う上位モデルに実務上かなり迫れる、というのが運用しての実感です。

## おわりに

Fable 5 のプロンプトガイドは、Fable 5 の使い方の説明であると同時に、「賢いモデルが内部で何をしているのか」の仕様書としても読めます。そう読むと、その工程を手持ちのモデルの外側に組む、という選択肢が見えてきます。

モデルの世代が上がるたびにハーネスを捨てるのではなく、計画・検証・記憶という基本構造は残して、閾値だけ緩めていく。そういう長く使える形を目指して設計しました。同じことを考えている方の参考になれば幸いです。
